# IBM Bob Remediation Prompt Template

This document explains the comprehensive prompt template used to instruct IBM Bob to generate fixes for code violations.

## Overview

The prompt template is designed to provide Bob with complete context while enforcing strict constraints to ensure safe, minimal, and style-preserving code fixes.

## Template Structure

The prompt is divided into three main sections:

### SECTION 1: CONTEXT

Provides Bob with all necessary information to understand the violation:

#### File Information
- **File Path**: Full path to the file being fixed
- **Programming Language**: Detected language (Python, JavaScript, Java, etc.)
- **Language Version**: If detectable (e.g., Python 3.x)
- **Affected Line(s)**: Line number(s) where the violation occurs
- **Total Lines**: Total line count for context

#### Complete File Content
- **CRITICAL**: The ENTIRE file content is provided, not just a snippet
- This allows Bob to understand:
  - Overall code structure and architecture
  - Existing code style and conventions
  - Dependencies and imports
  - Related functions and classes
  - Business logic context

#### Violation Details
- **Violation ID**: Unique identifier
- **Rule**: Rule ID and name (e.g., SEC-001 - SQL Injection)
- **Category**: SECURITY, GDPR, HIPAA, QUALITY
- **Severity**: CRITICAL, HIGH, MEDIUM, LOW
- **Description**: What the violation is
- **Explanation**: Why it's a problem
- **Recommendation**: How to fix it
- **Problematic Code**: The specific code snippet with the issue

### SECTION 2: FIX CONSTRAINTS

Enforces strict rules to ensure safe and minimal changes:

#### 1. Preserve Code Style
- Maintain existing naming conventions (camelCase, snake_case, PascalCase)
- Keep the same indentation style (spaces/tabs, indent size)
- Follow existing code formatting patterns
- Preserve all comments and docstrings
- Match the existing code organization

#### 2. Minimize Changes (Principle of Least Change)
- Only modify what is necessary to fix the violation
- Do NOT refactor unrelated code
- Do NOT change variable/function names unless required
- Do NOT modify imports unless they're part of the violation
- Keep changes localized to the problem area

#### 3. Preserve Functionality
- The fixed code MUST maintain the same behavior
- Do NOT alter program logic or control flow
- Ensure all function signatures remain compatible
- Keep all existing dependencies intact
- Maintain backward compatibility

#### 4. Language-Specific Requirements
- Use appropriate syntax for the detected language and version
- Follow language-specific security best practices
- Apply language-specific compliance standards
- Ensure compatibility with the language version

### SECTION 3: REQUIRED RESPONSE FORMAT

Specifies the exact JSON structure Bob must return:

```json
{
  "can_fix": true,
  "fix_description": "Brief description of what was changed and why",
  "patched_code": "THE COMPLETE CORRECTED FILE CONTENT",
  "changes_summary": [
    "Specific change 1",
    "Specific change 2"
  ],
  "risk_level": "low",
  "requires_manual_review": false,
  "confidence": 0.95
}
```

#### Field Descriptions

- **can_fix** (boolean): Whether Bob can safely fix the violation
- **fix_description** (string): 1-2 sentence explanation of the fix
- **patched_code** (string): **THE ENTIRE FILE** with the fix applied
  - CRITICAL: Must include every line from start to end
  - Not just the modified lines or a snippet
  - Complete, ready-to-write file content
- **changes_summary** (array): List of specific changes made
- **risk_level** (string): "low", "medium", or "high"
- **requires_manual_review** (boolean): Whether human review is needed
- **confidence** (float): Confidence score from 0.0 to 1.0

#### Response Requirements

1. **JSON Only**: Return ONLY valid JSON, no surrounding text
2. **No Markdown**: Do not wrap in markdown code blocks
3. **Complete File**: The `patched_code` must be the ENTIRE file
4. **Valid Syntax**: The patched code must have valid syntax
5. **If Cannot Fix**: Set `can_fix` to false and explain why

```python
def _generate_fix_prompt(self, file_path: str, file_content: str, 
                        violation: Violation, language: str) -> str:
    """
    Generate a comprehensive prompt for IBM Bob to fix a violation.
    
    Args:
        file_path: Path to the file being fixed

        language: Programming language of the file
        
    Returns:
        Formatted prompt string for IBM Bob
    """
```

## Why This Approach Works

### 1. Complete Context
By providing the entire file, Bob can:
- Understand the overall code structure
- Detect and maintain existing patterns
- Avoid breaking dependencies
- Preserve the code's architectural style

### 2. Strict Constraints
The constraints ensure:
- Minimal, surgical changes
- No unintended side effects
- Preservation of business logic
- Consistent code style

### 3. Structured Output
The JSON format ensures:
- Parseable, predictable responses
- Complete file content for easy application
- Metadata for validation and logging
- Clear success/failure indication

### 4. Safety First
Multiple safety mechanisms:
- Syntax validation before application
- Dry-run mode for testing
- Automatic backups before changes
- Risk level assessment
- Manual review flags

[detailed constraints as described above]

## Best Practices

1. **Always provide complete file content** - Never send just snippets
2. **Validate Bob's response** - Check JSON structure and syntax
3. **Use dry-run mode first** - Test fixes before applying
4. **Review high-risk fixes** - Human review for complex changes
5. **Keep backups** - Always create .backup files
6. **Log everything** - Track all changes for audit trails
